# Every update.php invocation is wrapped in `flock -n -E 0` against a per-type lockfile, so if a
# run is still going when the next one is due, the new one exits quietly (status 0, no cron mail)
# instead of piling up. Locks live in /run/lock, which is tmpfs and so clears on reboot.
#
# NOTE: the bare invocation below ("all") internally runs bills, summaries, full_text, dockets,
# meetings, code_sections and more. Its lock only stops "all" overlapping *itself*; it does not
# stop it running concurrently with an individually-scheduled job of the same type. See the note
# at the foot of this file.

# REMAINING OVERLAP, not solved by the per-type locks above:
# The bare "all" run at :01 duplicates work done by the individually-scheduled types, so e.g. the
# summaries job at :02 can run alongside "all" doing its own summaries pass. They take different
# lockfiles, so flock does not serialise them. Options, in rough order of preference:
#   1. Give update.php a single lock covering every type (lockfile keyed on the type list it will
#      run), so "all" and "summaries" genuinely exclude one another.
#   2. Drop the individually-scheduled lines whose types "all" already covers, and let "all" be the
#      only thing that runs them.
#   3. Reduce "all" to only the types not scheduled individually.
# Also worth noting: update.php calls set_time_limit(1200), a 20-minute ceiling, while `history`
# is scheduled every 10 minutes. Even with locking, a run that legitimately needs >10 minutes will
# cause every other history tick to be skipped.
